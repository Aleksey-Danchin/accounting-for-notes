15. Провайдер `AuthGuard`:

```tsx
<AuthGuard fallback={} loading={}>
  // content
</AuthGuard>

<AuthGuard fallback={} loading={}>
  {(user) => /* content */}
</AuthGuard>
```

`fallback` и `loading` — это `ReactNode | () => ReactNode`.

**fallback нет + loading нет**  
Children показывается как есть. В случае render-функции `user` берётся из стора.

**fallback есть + loading нет**  
Показывает плашку `fallback`, если пользователь прямо сейчас не авторизован, даже если идёт загрузка.

**fallback нет + loading есть**  
Показывает `loading` только при проверке пользователя. Независимо от того, авторизован пользователь или нет, показывает контент.

**fallback есть + loading есть**  
Тут должно быть всё понятно.

23. Нужно будет продумать систему `httpClient` на frontend на тот случай, если на один из запросов (или, если есть пул запросов, то на несколько) придёт `401`, чтобы refresh автоматически произошёл, все другие запросы в этот период ожидания дождались ответа от сервера об обновлении токенов и только потом пошли дальше, а те запросы, которые были отклонены во время истечения `access_token`, не возвращали ошибку, а дождались обновления и при успехе ещё раз были отправлены на сервер. Вообще полноценный менеджер запросов с возможностью приостановить очередь и вернуть в очередь из пула запросы при необходимости из-за необходимости воспользоваться `refresh_token`. Этот пункт можно обсудить — возможно, есть готовое решение в npm-пакетах.

24. На backend проходит ленивая проверка аутентификации `access_token`. В middleware к `request` закрепляется асинхронная функция, которая через замыкание имеет доступ к объекту `user` и флагу `isChecked`. Если `isChecked = true`, то просто возвращает `user`. Если нет — ходит в БД и проверяет.

25. В Redis не храним пользователя, только его `id`. В целом проверка пользователя будет занимать как минимум 2 запроса в хорошем сценарии: 1 в Redis, другой в БД о данном пользователе.
