# HTTP-клиент: свой менеджер

Статус: **готово к итерации разработки** (базовый auth уже есть). Этот файл — ТЗ / запрос на работу после обсуждения.

Сейчас: `apps/frontend/src/services/api/apiClient.ts` (axios + `p-limit`) и отдельно `authClient` с `withCredentials`. Нужен один менеджер на все вызовы к базовому API.

Готовые пакеты вроде `axios-auth-refresh` не берём — пишем сами.

---

## Что хочу по смыслу

Через менеджер проходят **все** запросы к базовому серверу (`VITE_API_BASE_URL`).

Если пользователь был в auth-режиме и вдруг получает **401**:

1. Внутренний механизм refresh.
2. Уже имеющиеся в очереди запросы, даже если они тоже вернутся с 401, **из очереди не уходят**.
3. Уходят те, что ответили **200** или **не-401** (4xx/5xx/сеть) — промис завершается, на replay после refresh их не гоняем.
4. Пока идёт refresh: **новые** запросы только копятся в очереди и **не уходят в сеть**; уже летящие не отменяем, остаются под учётом менеджера, пока волна не закончится.
5. Refresh начинаем по **первому** 401, не ждём, пока долетят все in-flight.
6. Успех refresh → прогоняем **остаток** очереди заново (в т.ч. бывшие 401). На элемент после успешного refresh — ровно одна новая попытка; снова 401 → reject этого элемента без новой волны. Позже 401 на другом запросе — новая волна ок.
7. Провал refresh = **force logout**: как обычный logout — reject остатка очереди и **`window.location.reload()`** (без обязательного POST `/auth/logout`). Не оставляем вкладку в полуживом auth-состоянии.

Если после провала refresh сессию не восстановили — после reload менеджер стартует заново; отдельный долгий «passthrough после fail» на той же загрузке страницы не нужен.

---

## Режимы и старт страницы

Менеджер при старте страницы определяет режим (login/logout и так делают reload — это хорошо ложится):

1. Короткий **boot-hold**: пока режим не выбран, запросы только в очереди, в сеть не идут.
2. `GET /api/auth/check` — **новый endpoint на backend**, тело **`0` | `1`** (не авторизован / авторизован по валидному access). Без обязательного guard; refresh cookie на этот path не придёт (Path refresh только `/api/auth/refresh`).
3. Если `check === 1` → режим **auth**.
4. Если `check === 0` → один **пробный** `POST /auth/refresh` (в blacklist, без hold-петли):
   - успех → **auth** (протухший access + живой refresh);
   - провал → **passthrough** (аноним или сессия мертва).
5. Потом при auth — как сейчас bootstrap `me` для user в store.

Режимы:

- **passthrough** — запросы в сеть сразу (GET с concurrency); 401 наружу; refresh не трогаем.
- **auth** — очередь + hold/refresh/replay.
- **refresh-hold** — подсостояние auth на время волны.

## Настройки менеджера

- **Concurrency только для GET** (свой лимит вместо `p-limit`). POST/PUT/PATCH/DELETE без этого лимита.
- **Blacklist** URL, которые так (hold/auto-refresh) обрабатывать не нужно, чтобы не попасть в петлю: как минимум `/auth/login`, `/auth/logout`, `/auth/refresh`, `/auth/check`.
- `withCredentials: true` на всём клиенте к API.

---

## Cookies (контекст)

- `access_token` — httpOnly, Path под `/api`
- `refresh_token` — httpOnly, Path только `/api/auth/refresh`
- Ротация refresh на backend жёсткая: старая сессия уничтожается, новая создаётся. Параллельные refresh с двух вкладок опасны.

---

## Несколько вкладок

Нужно сразу продумать: два менеджера не должны одновременно сделать refresh и словить панику на сервере (вторая ротация со старой cookie → 401 → ложный разлогин).

Берём услуги браузера:

- **Web Locks** — mutex на имя вроде `afn-auth-refresh`: в критической секции refresh в один момент только одна вкладка.
- **BroadcastChannel** — рация: `refresh-ok` / `refresh-fail`; остальные вкладки replay очереди или тоже force logout (reload).
- **localStorage-маркер** свежего refresh — чтобы вкладка, получившая замок сразу после лидера, не сделала второй HTTP refresh.

Лидер волны = кто **первым взял** lock (обычно кто раньше обработал 401). Это не постоянная роль.

Если вкладку-лидера закрыли до ответа refresh: lock отпускается сам, следующая вкладка продолжает. **Grace / повторная выдача той же пары токенов на backend не делаем** (волевое решение по безопасности): если сервер уже ротировал, а Set-Cookie не дошёл — сессия потеряна, дальше 401 → force logout. Не хотим окно ~30 с, в котором злоумышленник со старым refresh снова получает живые токены. Обычный multi-tab без убийства mid-flight закрываем lock + channel + маркер.

Fallback без Web Locks не делаем в этой итерации.

## Раскладка (ориентир)

- Frontend: `services/api/httpManager.ts` + тонкий фасад `apiClient`; `concurrency.ts`; конфиг (baseURL, concurrency, blacklist, имена lock/channel/marker).
- Удалить отдельный `authClient`, убрать зависимость `p-limit`; auth API на общий клиент.
- Backend: `GET /auth/check` → `0|1`.
- Менеджер не импортирует `sessionStore` (цикл модулей); reload сам сбрасывает состояние.
- После кода — обновить rules (`frontend.mdc`, при необходимости `backend.mdc`) только после явного approve.

Вне скоупа этой итерации: e2e multi-tab, grace/reuse токенов, theft detection семейства refresh.

---

## Критерии приёмки

- Все вызовы к базовому API через менеджер
- GET с concurrency; не-GET без этого лимита
- Boot: check → при 0 пробный refresh → режим; boot-hold до выбора режима
- Auth + 401 → hold; новые не в сеть; 200/не-401 уходят; 401 остаются; refresh ok → replay остатка (один retry на элемент за волну)
- Blacklist не триггерит hold
- Refresh fail → reject + reload (и другие вкладки по каналу)
- Две живые вкладки: один успешный HTTP refresh на волну
- Без `p-limit` и без `axios-auth-refresh`
